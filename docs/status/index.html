Status

Fuxedo is under active development and usable today for development and testing. The compatibility suite runs unmodified against Oracle Tuxedo 12.2.2 and 22.1 on every commit; that is the project's definition of "matches".

Proven by running, not by claims

Three bodies of existing code run against fuxedo today, each with the same claim: no source edits, rebuild and go.

EstateResult
Oracle's C samples simpapp, xmlfmlapp, and qsample from the Oracle Tuxedo 12.2.2 samples build with fuxedo buildclient/buildserver and boot from their own UBBCONFIG; simpapp and xmlfmlapp also run against Oracle 12.2.2 itself with identical output.
Book examples Every runnable example from Oracle Tuxedo for Developers executes on fuxedo, including the Oracle Database chapter against a live 21c XE; the same test code runs on Oracle 12.2.2 to catch drift.
Python bindings tuxedo-python builds and runs unmodified against fuxedo, demo application included.

Done and verified

AreaCoverage
ATMI client/server tpinit/tpterm, tpcall, tpacall/tpgetrply/tpcancel with flag semantics, tpforward, tpreturn, tpadvertise/tpadvertisex incl. TPSINGLETON and TPSECONDARYRQ, conversational tpconnect/tpsend/tprecv, automatic transactions and AUTOTRAN, late-reply draining.
Typed buffers FML32 with Oracle-compatible field ids and boolean expressions, VIEW32 with viewc32/viewdis32 and the Fv* family, XML buffers with tpxmltofml32 and BUFTYPECONV, STRING, CARRAY, tpimport/tpexport.
Administration tmloadcf, tmunloadcf, tmboot, tmshutdown, tmadmin, qmadmin, ud32, tmipcrm, crdl/crlog, the TM_MIB classes, runtime updates (advertise, unadvertise, suspend, resume, chgserver, changetrace), printtrans and offline log utilities.
Operations MSSQ sets with secondary queues and REPLYQ, server restart with MAXGEN/RESTART/GRACE sliding window, data-dependent routing across groups incl. boot-order fallthrough for staged rollouts.
Transactions Multi-group two-phase commit with per-group TMS servers, folder TLOG with heuristic records and crash recovery, transactions over workstation links, cross-domain 2PC through GWTDOMAIN with persistent remote branches, Oracle Database XA via buildtms, transactional /Q.
Eventing tpsubscribe/tpunsubscribe with FML filters, tppost, tpnotify, tpbroadcast, unsolicited messages, TMUSREVT/TMSYSEVT, Oracle-compatible on-disk subscription database.
/Q Queue spaces as folders, messages as files, tpenqueue/tpdequeue with TPQCTL, TMQUEUE, TMQFORWARD, future-dated messages, qmadmin.
Networking GWTDOMAIN domain gateways with dmadmin, DMTLOG, links encrypted by default with trust-on-first-use pins, workstation clients via WSL and WSNADDR.
Observability ULOG, changetrace, printtrans, USDT probes (provider "fuxedo") at the ATMI, transaction, XA, /Q, and domain-wire boundaries, plus uprobe-friendly builds for bpftrace.
Verification C and Python compatibility suites run against Oracle Tuxedo 12.2.2 and 22.1 in CI, an invalid-argument hardening suite guards the API surface, and the API reference documents each call with tested examples.

Not prioritized yet

Nothing on this list is refused work; it is work ordered by demand. Fuxedo develops in the open, and the defaults below reflect what migrating estates ask for first. Anything here can move up on request, and larger items can be commissioned as consultancy. Two examples of the difference: Java access defaults to a library over fuxedo's encrypted workstation protocol; a wire-compatible JOLT listener with repository servers is buildable, just not the default path. The same applies to multi-machine MP clustering and COBOL support.

ItemState
tmadmin diagnostics Core commands covered; the deeper diagnostic surface (bbparms, dump-style shared memory inspection, extended statistics) is thin.
FML32 indexes Not stored; flat layout by design, at a small lookup cost.
WSH process model Workstation listener serves clients in one process today.

Roadmap

In rough order: the Java client library over the workstation protocol, the remaining tmadmin surface, WSH-style multiprocess serving, then depth (more Oracle versions in the CI matrix, more probes). The gap list and the API coverage matrix live in the repository, updated as items land.
